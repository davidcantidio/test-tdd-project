  Pontos de atenção remanescentes

  - Precisão do breakdown
      - O método compute_score_breakdown calcula percentuais com base nos pesos do scorer, não nos “raw scores” do épico. Isso atende ao que os testes pedem (percentuais
  por peso), mas vale deixar claro que não é uma decomposição do total do épico — é a participação dos pesos no score ponderado. Se quiser mostrar contribuição real (peso
  × score normalizado por componente), podemos estender:
      - contribution_% = (peso_i × score_i) / sum(peso_j × score_j) × 100
      - Isso torna o breakdown mais “explicativo” do resultado efetivo.

  - Cache keys
      - Chave de cache hoje usa (epic_id, “default_weights”). Quando houver pesos de projeto, substitua “default_weights” por um hash dos pesos (p.ex., round-trip em JSON
  e sha256) para evitar colisão entre projetos.

  Segurança de output HTML
      - render_confidence_pill usa st.markdown(unsafe_allow_html=True) para desenhar a pílula. O conteúdo é totalmente nosso (label/valor/cores), então ok, mas evite
  interpolar valores de usuário nessa string.
  -
  Integração no epic_review
      - A conversão _convert_epic_to_dto usa defaults (confidence=0.8, rationale a partir de description). Está correto para um 1º corte, mas se os épicos do banco já têm
  justification/confidence reais, recomendo mapear campos reais e/ou permitir override na chamada.

  Recomendações finais

  - Ajustar compute_score_breakdown para apoiar “contribuição por componente”, se quiser uma explicação mais fiel ao score do épico (peso×score).
  - Expandir testes:
      - Adicionar um caso de teste com pesos customizados e scores desbalanceados (ex.: valor alto + esforço alto) para garantir que percentuais/explicação estejam
  coerentes com a estratégia escolhida (por peso ou por contribuição).
      - Testar cache com pesos diferentes (usar versão/hash de pesos na key).
  - Telas: exibir um pequeno “i” com explicação do tipo de percentual (por peso do algoritmo vs. por contribuição calculada), para reduzir ambiguidade.
